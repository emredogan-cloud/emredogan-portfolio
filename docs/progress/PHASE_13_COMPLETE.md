## A deliberate deviation from the roadmap, and the reasoning

The roadmap asks for a **3 engines × 3 breakpoints × 8 sections visual
regression matrix**. What was built asserts **geometry and capability** on all
three engines, and keeps pixel baselines on Chromium.

Three reasons, in order of weight:

1. **WebKit baselines cannot be produced on this machine.** Its Playwright
   build needs `libevent-2.1-7t64`, which needs root. A WebKit baseline set
   would have to be generated by CI and committed unseen — which is not a
   review, it is a rubber stamp with extra steps.
2. **Most of a cross-engine pixel diff is antialiasing.** Font rasterisation
   differs between engines by design. A suite whose diffs are usually noise
   teaches everyone to re-record without looking, which is worse than no suite.
3. **What actually breaks between engines is layout and capability**, not
   antialiasing: a grid that collapses, an `aspect-ratio` that resolves
   differently, `backdrop-filter` silently unsupported, `color-mix` failing to
   parse, an image format not negotiated. Every one of those is measurable
   exactly, on every engine, and does not rot when the design changes.

So: 15 layout assertions per engine, 6 capability probes per engine, and the
Chromium pixel baselines that are good at catching design regressions.

## What the matrix asserts

| Check              | Detail                                                                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Sections render    | All five have a real box, a visible heading, and never exceed the viewport width                                                                             |
| Column behaviour   | The work grid is one column below 1024 px and two at or above it — an engine mis-resolving the template shows up immediately                                 |
| Marquee and footer | Present at every breakpoint                                                                                                                                  |
| Capabilities       | `color-mix`, `aspect-ratio`, custom properties, `dvh`, `clamp` — all load-bearing, all asserted true                                                         |
| `backdrop-filter`  | Either the blur works **or** the fallback background is opaque enough to read against. A transparent panel over moving content is the failure this rules out |
| Image negotiation  | Every `/_next/image` response is AVIF or WebP on every engine — none is served the original JPEG                                                             |
| Native `<dialog>`  | The mobile menu is the platform modal, not a hand-rolled one                                                                                                 |

A bug in the first version of the column check is worth recording: it counted
**fifteen columns** because `#work li` matched the stack pills inside each card
as well as the grid items.

## Engine differences found, and how each is handled

| Difference               | Where                                                                                                                   | Handling                                                                                                                                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `forced-colors` keywords | WebKit's emulation resolves `Canvas` to silver but leaves `color` alone — white on `#c0c0c0`, **1.81:1**, 163 axe nodes | Every forced-colors declaration now ships a concrete colour _before_ the system keyword. A supporting engine takes the keyword and the reader's palette wins; one that does not keeps a readable pair |
| Forced-colors palette    | Chromium emulates a **light** canvas, Firefox a **dark** one                                                            | Both run in CI. The `color-mix` bug fixed in Phase 12 was visible only under Firefox's dark palette                                                                                                   |
| Clipboard permissions    | `clipboard-read` ungrantable in Firefox and WebKit                                                                      | Real clipboard contents asserted on Chromium; accessible name asserted everywhere                                                                                                                     |
| `performance.memory`     | Chromium only, and quantised to a flat 10,000,000                                                                       | Heap read through CDP, Chromium only                                                                                                                                                                  |
| Frame pacing under load  | Headless WebKit on CI delivers frames erratically                                                                       | The marquee publishes `data-marquee="stopped"` instead of tests inferring rest from pixels                                                                                                            |

## Limitations, stated

1. **No real Safari, Edge or Samsung Internet.** WebKit in CI is the engine, not
   the browser: Safari's own UI, its extensions and iOS-specific behaviour are
   unverified. Tier 2 remains "expected to work, spot-checked" and this phase
   did not change that.
2. **Pixel baselines are Chromium-only**, by the reasoning above.
3. **No physical device**, unchanged from Phase 10.
