# Browser support matrix

Last reviewed: 2026-08-19 (Phase 13).

## Tier 1 — fully supported, tested in CI on every pull request

| Engine                                | Versions     | How it is verified                       |
| ------------------------------------- | ------------ | ---------------------------------------- |
| Chromium (Chrome, Edge, Brave, Opera) | last 2 major | Playwright E2E + axe + visual regression |
| Gecko (Firefox)                       | last 2 major | Playwright E2E + axe                     |
| WebKit (Safari macOS/iOS)             | Safari 17+   | Playwright E2E + axe                     |

### How the three engines are actually verified

| Layer                                                                                                           | Chromium | Firefox | WebKit |
| --------------------------------------------------------------------------------------------------------------- | -------- | ------- | ------ |
| Functional E2E                                                                                                  | ✅       | ✅      | ✅     |
| axe (WCAG 2.2 AA)                                                                                               | ✅       | ✅      | ✅     |
| Cross-engine layout matrix — 5 sections × 3 breakpoints                                                         | ✅       | ✅      | ✅     |
| Capability probes (`color-mix`, `aspect-ratio`, `dvh`, `backdrop-filter`, image negotiation, native `<dialog>`) | ✅       | ✅      | ✅     |
| Pixel baselines                                                                                                 | ✅       | —       | —      |

**Pixel baselines stay on Chromium, and that is a deliberate deviation from the
roadmap**, which asks for a 3 × 3 × 8 visual-regression matrix. Three sets of
pixel baselines make every intentional design change a three-way re-record, and
font rasterisation differs enough between engines that most of the resulting
diff is antialiasing — noise that trains everyone to re-record without looking.
WebKit baselines also cannot be produced on the development machine at all (see
_Known local limitation_), so that set would have to be generated by CI and
committed unseen, which is not a review.

What genuinely differs between engines is **layout and capability**, not
antialiasing: a grid that collapses, an `aspect-ratio` that resolves
differently, `backdrop-filter` silently unsupported, `color-mix` failing to
parse, an image format not negotiated. `tests/e2e/cross-browser.spec.ts`
asserts all of those on all three engines, which is a stronger guarantee than a
screenshot and does not rot.

## Tier 2 — expected to work, spot-checked manually

Samsung Internet (last 2), Chrome on Android (last 2), Safari on iPadOS (17+).

## Tier 3 — content remains readable, enhancements degrade

- **JavaScript disabled.** Every route is statically prerendered, so all
  content and in-page navigation work. Motion and the animated background do
  not run.
- **No Canvas 2D context.** The background falls back to a static CSS gradient.
- **`prefers-reduced-motion: reduce`.** Meteors stop, the marquee stops,
  reveals resolve instantly. No information is lost.
- **`forced-colors: active`** (Windows High Contrast). Gradient text falls back
  to a solid system colour — `background-clip: text` is unsupported there and
  would otherwise render the word invisible.

## Not supported

Internet Explorer, and any browser without support for CSS custom properties,
`color-mix()`, or ES2022. No polyfills are shipped for these.

## Platform features and their fallbacks

| Feature                         | Used for                           | Fallback                          |
| ------------------------------- | ---------------------------------- | --------------------------------- |
| `color-mix()`                   | Translucent surfaces and hairlines | Baseline in all Tier 1 engines    |
| `backdrop-filter`               | Navigation island, glass cards     | Opaque surface token              |
| `animation-timeline: scroll()`  | Scroll progress bar                | JS-driven progress                |
| `text-wrap: balance` / `pretty` | Headline and paragraph ragging     | Normal wrapping                   |
| `dvh` units                     | Full-height sections on mobile     | `vh`                              |
| AVIF                            | Images                             | WebP, then JPEG, via `next/image` |

## Known engine differences, and what is done about them

| Difference                      | Engines                                                                                                     | Handling                                                                                                                                                                                                     |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `forced-colors` system keywords | WebKit's emulation resolves `Canvas` to silver while leaving `color` untouched — white on `#c0c0c0`, 1.81:1 | Every forced-colors declaration ships a concrete colour _before_ the system keyword. A supporting engine takes the keyword and the reader's palette wins; one that does not keeps a guaranteed-readable pair |
| Forced-colors palette           | Chromium emulates a **light** canvas, Firefox a **dark** one                                                | Both are exercised in CI. A `color-mix()` bug that produced 1.58:1 was visible only under Firefox's dark palette                                                                                             |
| Clipboard permissions           | `clipboard-read` cannot be granted in Firefox or WebKit                                                     | The real clipboard contents are asserted on Chromium; the control's accessible name is asserted everywhere                                                                                                   |
| `performance.memory`            | Chromium only, and quantised to uselessness                                                                 | Heap is read through CDP `Performance.getMetrics`, Chromium only                                                                                                                                             |
| Frame pacing under load         | Headless WebKit on CI delivers frames erratically                                                           | The marquee publishes `data-marquee="stopped"` rather than tests inferring rest from pixel positions                                                                                                         |
| Font rasterisation              | All three differ                                                                                            | Pixel baselines on Chromium only; layout asserted by geometry everywhere                                                                                                                                     |

## Known local limitation

Running the WebKit suite on a Linux workstation requires the system package
`libevent-2.1-7t64`:

```bash
sudo apt-get install libevent-2.1-7t64
# or: sudo pnpm exec playwright install-deps
```

CI installs it automatically (`playwright install --with-deps`), so WebKit is
always covered on pull requests even when it cannot run locally.
